### SOLID

| 字母  | 原则                  | 核心意思     |
| ----- | --------------------- | ------------ |
| **S** | Single Responsibility | 单一职责原则 |
| **O** | Open/Closed           | 开闭原则     |
| **L** | Liskov Substitution   | 里氏替换原则 |
| **I** | Interface Segregation | 接口隔离原则 |
| **D** | Dependency Inversion  | 依赖倒置原则 |

#### *S：这个东西是不是管太多了？

一个模块只负责一类事情。

```
一个组件干了 10 件事情
        ↓
考虑拆分
```

#### *O：以后增加需求，是不是又要改一大堆 if？

新增需求时，尽量通过扩展，而不是不断修改原有核心逻辑。

```
if A
if B
if C
if D
        ↓
考虑策略 / 配置 / 插件化
```

#### L：这个实现能不能真正替换原来的实现？

子类型应该能够替换父类型，而不会破坏原来的程序行为。

```
A 类型
 ↓
B 类型

B 替换 A 后
原来的代码还能不能正常运行？
```

#### I：是不是所有地方都依赖了一个巨大的接口/模块？

不要让一个模块依赖它根本不需要的接口。

```
巨大 UserService
        ↓
拆成多个小接口
```

#### *D：业务代码是不是和具体实现绑死了？

高层模块不要直接依赖具体实现，而应该依赖抽象。

```
业务
 ↓
axios

业务
 ↓
具体数据库/API/SDK
```

如果换实现就必须大量修改：

> 考虑抽象一层。

区域负责驱动。

配置负责页面。

数据中心负责数据。

组件负责展示。



### 第一层：Region Store

负责当前区域状态。

### 第二层：Dashboard Config

决定当前区域展示哪些组件。

### 第三层：Widget Registry

负责组件动态加载。

### 第四层：Data Center

统一管理接口请求、缓存、刷新。

每个组件只负责展示，不关心区域切换逻辑。



## 区域上下文层

### RegionStore

统一管理：

```
interface RegionContext {
  level: string
  regionCode: string
  regionName: string
}
```

例如：

```
{
  level: "town",
  regionCode: "330102001",
  regionName: "XX镇"
}
```

系统所有模块仅从此处获取区域信息。

禁止：

```
this.level = 'city'
```

这种局部状态。

export default {

schema[level]

生成页面。
